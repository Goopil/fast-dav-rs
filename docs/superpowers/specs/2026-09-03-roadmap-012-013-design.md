# Roadmap 0.12 / 0.13 — design

**Date**: 2026-09-03 · **Status**: approved (user) · **Supersedes**: n/a
**Context**: post-0.11.0 release; pre-0.11.0 roast closed (PR #143, #144–#153), issue #154 backlog open.

## Goals

Move the crate from "spec-conformant core, SabreDAV-only-tested" to "usable in production
against heterogeneous servers", then extend the protocol surface. Two cycles:

- **0.12 — real-world usage**: sync session + full-list fallback, discovery hardening,
  multi-server e2e fixtures, pluggable OAuth, examples + docs sweep.
- **0.13 — protocol**: RFC 6638 scheduling, RFC 8607 attachments, RFC 7809 timezones
  (verify + docs), typed `current-user-privilege-set` exposure. **No RFC 3744 ACL.**

## Decisions (user-approved)

| Decision | Choice |
|---|---|
| Cycle split | 2 releases; DX/interop first (0.12), protocol extensions second (0.13) |
| Sync API | In-memory `SyncSession` per collection (`initial()` / `incremental()` → typed deltas); caller persists the sync token; no sqlite (YAGNI vs vstorage) |
| Sync algorithm | DAVx⁵ state machine: probe `supported-report-set` → `sync-collection` when supported → transparent full-list fallback (PROPFIND + multiget) → **reset to initial sync on invalid token** (403 `valid-sync-token` / 410) → conflicts: server wins |
| OAuth | Small + non-invasive: pluggable `TokenProvider` trait + generic refresh grant (RFC 6749 §6), pure HTTP, auto-renew Bearer. No browser flows, no provider-specific logic in core |
| ACL | Not implemented (no mainstream server implements RFC 3744 for real: shared calendars are OCS/custom/absent). Cheap alternative: typed exposure of `current-user-privilege-set` in PROPFIND results (0.13) |
| E2E fixtures | Radicale (different engine, invalidatable sync-tokens, no LOCK, auto-create quirk) + Nextcloud (real-world target, OIDC/Bearer, VTODO) + an opt-in `#[ignore]` smoke tier against **Provider A** (unauthenticated shapes only, zero credentials). Baïkal skipped (same engine as SabreDAV). Google/iCloud not dockerizable — manual tier only |
| Examples | Full suite (~8) in a new `examples/` dir, pairing with the `icalendar` crate (parsing stays out of the crate) |
| Provider A naming | The real provider is never named in repo artifacts (spec, issues, PRs, examples, CHANGELOG, code). Designation: **"Provider A"**. No production URL hardcoded; smoke tier reads `PROVIDER_A_DAV_URL` from env, skipped when absent |
| Provider A quirks | Encoded as unit fixtures with anonymous XML bodies: principal-404-after-auth, VTODO-on-calendar, CATEGORIES contact groups, UTF-8 double-encoding detector |

## Research basis

- **libdav** (Rust): typed request API, SRV+TXT discovery (explicitly deferred — needs a
  DNS resolver dep; backlog), `CheckSupport` capability probing.
- **vstorage/pimsync** (Rust): stateful sync sessions, evidence that etag/hash full-poll
  is the robust two-way strategy; deletion protections.
- **DAVx⁵** (Android, reference client): the sync algorithm adopted for P3; per-provider
  login presets; `If-Schedule-Tag-Match` for 0.13 scheduling.
- **python-caldav**: transparent sync fallback API (the P3 fallback pattern);
  compatibility-hints architecture (named per-provider profiles with per-feature support
  levels — backlog).
- **tsdav**: OAuth helper shape (exchange, cache refresh token, transparent renewal) —
  the shape P4 borrows.
- **Radicale**: highest-value second fixture (different XML layer, sync-token cache
  invalidation, no LOCK, no RFC 3744).
- **Provider A** (public sources, 2026-09): DAV = Basic + app passwords only (username =
  internal short id, not email); OAuth2 documented for REST API only — unverified on DAV;
  sync-token support unverified anywhere → fallback is not speculative; principal-404
  after successful auth with wrong username form (never 401); `.well-known` unreliable;
  CardDAV write path double-encodes some 3-byte UTF-8 sequences (data corruption,
  community-verified, reported); inbox/outbox collections exist (scheduling plausible,
  unverified); shared calendars NOT exposed via DAV (⇒ ACL has no real-world target).

## 0.12 work packages

### P1 — E2E fixtures: Radicale + Nextcloud + Provider A smoke tier (first — P3 depends on it)
- Docker fixtures modeled on `sabredav-test/` (compose, setup/reset scripts, CI job).
- Radicale: official image, Basic auth, exercise sync-token invalidation (cache wipe),
  no-LOCK robustness, auto-create-on-GET quirk.
- Nextcloud: Bearer/OIDC token auth, VTODO coverage, heaviest image — build last.
- Provider A smoke tier: `#[ignore]` e2e hitting `PROVIDER_A_DAV_URL` (OPTIONS `/`,
  `GET /.well-known/caldav|carddav`, unauthenticated PROPFIND shape) — asserts 401 +
  `WWW-Authenticate: Basic` present, records well-known shape. Skipped when env unset.
  3 requests/run, opt-in only, never in default CI.
- **Acceptance**: both fixtures green locally (setup + reset + one CRUD test each),
  CI job wiring reviewed, smoke tier documented.

### P2 — Discovery hardening
- First-class error for "auth OK but principal 404" (the Provider A wrong-username-form
  failure mode) with an actionable message; distinct from transport errors.
- Discovery order: principal root PROPFIND before/alongside `.well-known`.
- Reusable typed probe of the `OPTIONS` `DAV:` compliance header (classes 1/2/3,
  `access-control`, `calendar-access`, `addressbook`, …) exposed as a public helper.
- Unit tests with the Provider A shapes (anonymous XML fixtures); e2e on Radicale+NC.
- **Acceptance**: wrong-principal-404 produces a named error variant with a clear
  message; DAV: header parse is public + tested; no regression in existing discovery.

### P3 — `SyncSession` + transparent full-list fallback
- `webdav::sync` (new module) or `SyncSession` in `webdav/client.rs` (decide by file
  size): holds collection path, capability probe result, last token, typed delta.
- `initial()` → full state; `incremental()` → added/modified/deleted typed deltas;
  `resynced` surfaced; fallback = PROPFIND Depth:1 + etag diff + multiget batching.
- CalDAV and CardDAV thin wrappers share the engine (duplication gate ≤3%).
- Invalid/unsupported token → transparent reset to initial sync (DAVx⁵ rule), flagged.
- **Acceptance**: unit (mock server: supported, unsupported, invalid-token, 403
  `valid-sync-token`, 507-continuation) + e2e invalid-token on Radicale + happy path on
  SabreDAV + NC; CHANGELOG + README sections; Sonar coverage ≥80% on new code.

### P4 — Pluggable auth: `TokenProvider` + refresh
- Trait `TokenProvider` (`token(&self) -> Result<String>` + optional expiry) wired into
  the request pipeline as an alternative to static Basic/Bearer.
- Generic refresh grant impl (RFC 6749 §6): token endpoint URL, client_id/secret,
  refresh_token → access_token, transparent renewal on 401/expiry. Pure HTTP.
- No browser flows, no provider presets (Nextcloud Login Flow v2 = backlog, opt-in
  feature if ever wanted).
- **Acceptance**: unit tests with a mock token endpoint (initial, renewal on 401,
  refresh-failure error taxonomy); builder option documented; Basic/Bearer unchanged.

### P5 — Examples + docs sweep
- New `examples/`: getting-started (discovery + CRUD), full sync loop (with `icalendar`
  crate), Nextcloud client, Radicale client, streaming large collections, locking,
  multiget batching, typed error handling. `cargo build --examples` in CI (already
  wired, currently a no-op).
- Docs sweep: README sections for everything added in 0.11+0.12; API doc comments;
  AGENTS.md sync; UTF-8 double-encoding quirk documented + read-back helper considered.
- **Acceptance**: `cargo run --example` works per example against a local fixture;
  README updated; docs reviewed against code.

### Waves
- Wave 1 (parallel): P1 ∥ P2 ∥ P4 (disjoint file domains: `tests/e2e`+CI ∥ `discovery.rs` ∥ `builder.rs`/`common/`)
- Wave 2: P3 (uses Radicale fixture from P1; touches `webdav/client.rs` + new sync module)
- Wave 3: P5 (documents the final API surface)
- Then release 0.12.0 (user go required).

## 0.13 sketch (re-brainstorm lightly at that point)

- **Scheduling RFC 6638**: probe `calendar-user-address-set` + inbox/outbox discovery +
  POST outbox (iTIP) + inter-principal free-busy + `If-Schedule-Tag-Match` conditional
  writes. Prerequisite: live capability verification against Provider A (inbox/outbox
  exist, function unknown — Issue 2 questionnaire).
- **Attachments RFC 8607** (small: POST + `managed-id`).
- **Timezones RFC 7809**: verify + document + pair with `calcard`/`icalendar`; parsing
  stays caller-side.
- **Typed `current-user-privilege-set`** in PROPFIND results (no ACL writes).
- Backlog: DNS SRV+TXT discovery (RFC 6764 §3, needs a DNS resolver dep),
  compatibility-hints per provider, WebDAV Push draft.

## Constraints & conventions

- Provider A is never named; no production URL in the repo (env-gated smoke tier).
- Pipeline per package: issue → worktree + subagent → review + spot-check → local gates
  (fmt, clippy `-D warnings`, nextest unit `--all-features --locked`, doctests,
  `CARGO_TARGET_DIR=target`) → PR → **CI 12/12 verified explicitly** → squash merge →
  CHANGELOG union on conflicts.
- SonarCloud gates mandatory: coverage ≥80% new code, duplication ≤3% (share via
  `webdav/`/`common/`, never copy-paste caldav↔carddav).
- Docs kept in sync (README, AGENTS.md, doc comments) — stale docs are bugs.
- Release only on explicit user go (publish.yml triggers on GitHub Release published).

## Risks

- Nextcloud Docker fixture is heavy (image pull, slow boot) — mitigate with healthcheck
  + pre-pulled image in CI cache; Radicale is trivial by contrast.
- `SyncSession` API shape may need adjustment after P1 fixtures reveal real server
  differences — keep the struct small, iterate in 0.13 if needed.
- Provider A behaviors are community-sourced; the smoke tier and unit fixtures encode
  them without hard-coding any assumption the provider could break silently.
