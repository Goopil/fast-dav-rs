# Revue de code adversariale — fast-dav-rs

- **Date :** 2026-09-08
- **Révision auditée :** `ba4bcca` (v0.15.0, branche main)
- **Méthode :** audit adversarial en 4 axes — sécurité (auth/TLS/headers/XML),
  logique client & sync (retry, RFC 6578, multiget), couche XML (streaming,
  namespaces, DoS), caldav/carddav + écart docs/CI vs réalité. Chaque finding
  a été re-vérifié à la main avant d'être listé ; un faux positif a été chassé
  et documenté en fin de rapport.
- **Bilan :** 1 critique · 1 high · 12 medium · 12 low · 1 faux positif écarté.

## 🔴 CRITIQUE

### 1. Le crate publié ne compile pas — `docs/` absent du `include`

**Où :** `Cargo.toml:14` ; `src/lib.rs:1-5`

`include` liste `["Cargo.toml", "LICENSE", "README.md", "src/**/*.rs", "examples/**/*.rs"]`,
mais `src/lib.rs` fait `include_str!("../docs/error-handling.md")`,
`advanced-configuration.md`, `streaming-and-sync.md`, `e2e-testing.md`.
Invisible en local et en CI car rien ne teste le packaging.

**Reproduction :**

```bash
cargo package --list --allow-dirty | grep -c '^docs/'   # → 0 (les 4 fichiers manquent)
cargo publish --dry-run                                  # → échec de compilation : fichiers inclus introuvables
```

**Correctif :** ajouter `"docs/**/*.md"` au tableau `include` (1 ligne) et
ajouter un step `cargo publish --dry-run` (ou `cargo package`) dans la CI
pour verrouiller le point.

## 🟠 HIGH

### 2. Le fallback sync supprime des données locales sur une erreur transitoire

**Où :** `src/webdav/sync.rs:514` (filtre), `:699-702` (diff `deleted`)

Sur le chemin de repli PROPFIND (serveur sans `sync-collection`), `propfind_state`
écarte du `current` tout item portant un statut d'erreur par-item (4xx/5xx
dans le 207 — `has_error_status` = code >= 400, sync.rs:606-610).
`diff_maps` déclare alors `deleted` tout href présent dans `prev` et absent
de `current`. Résultat : un 500/403 **transitoire** sur un seul membre fait
apparaître cet item dans `SyncDelta.deleted` — et l'appelant qui suit
l'algorithme documenté (DAVx⁵) supprime sa copie locale.

Le chemin `sync-collection` gère ce cas correctement : `diff_rows` (sync.rs:650-651)
**skippe** les lignes en erreur sans jamais les supprimer. La logique correcte
existe déjà, le fallback ne l'utilise pas.

**Reproduction (scénario filaire) :**

1. Session initialisée : `PROPFIND Depth: 1` renvoie `/cal/e1.ics`
   (`getetag: "1"`). `prev = {"/cal/e1.ics": Some("\"1\"")}`.
2. `sync_session.incremental()` → nouveau `PROPFIND Depth: 1` ; le serveur
   renvoie un 207 où la réponse `/cal/e1.ics` porte
   `<D:status>HTTP/1.1 500 Internal Server Error</D:status>` (glitch
   backend, l'item existe toujours).
3. Observé : `SyncDelta.deleted == ["/cal/e1.ics"]` → l'appelant détruit la
   donnée locale. Attendu : item ignoré cette passe (ou erreur explicite),
   jamais classé `deleted`.

**Correctif :** dans le fallback, traiter les items en erreur comme
`unknown` : les exclure de la diff *et* de la suppression (même sémantique
que `diff_rows` sync.rs:650), ou propager une erreur pour que l'appelant
puisse réessayer sans perdre l'état.

## 🟡 MEDIUM

### 3. Flag `truncated` avalé — résultat partiel présenté comme complet

**Où :** `src/webdav/sync.rs:410-421` ; mécanique : `src/webdav/types.rs:898` (507 → `truncated`)

`sync_pages` boucle tant que le serveur fournit un token **différent** ;
si le serveur tronque (507 dans le 207) et renvoie le même token — ou pas
de token — la boucle s'arrête et retourne les lignes partielles comme
snapshot complet. Le flag `truncated` est consommé localement et jamais
remonté : `SyncDelta`/`SyncSnapshot` n'ont ni champ `truncated`, ni
`resync`, ni erreur. Les membres des pages non retournées restent
invisibles jusqu'à leur prochain changement.

**Reproduction (filaire) :** `sync-collection` REPORT avec token `T1` ;
réponse 207 contenant 1 membre sur 3, un response avec
`<D:status>HTTP/1.1 507 Insufficient Storage</D:status>`, et
`<D:sync-token>T1</D:sync-token>` (identique). → `incremental()` retourne
`Ok` avec 1 item, état final présenté comme complet.

**Correctif :** propager `truncated` dans `SyncDelta` (ou convertir en
erreur/flag `must_resync`) pour que l'appelant puisse forcer un resync.

### 4. Un 403 nu épinglé `Unsupported` à vie

**Où :** `src/webdav/sync.rs:325-337`

Un 403 **sans** la precondition `valid-sync-token` (ACL flap, maintenance,
quota) déclenche la même re-probe qu'un reset de token, mais épingler
la capacité à `Unsupported` pour toute la durée de vie de la session :
toutes les sync suivantes passent en PROPFIND+multiget lent, sans re-probe
ni signal. La donnée reste correcte ; la performance se dégrade en silence.

**Reproduction :** premier `incremental()` contre un serveur qui répond
403 nu une fois ; rétablir le serveur ; `incremental()` suivant utilise
toujours le fallback.

**Correctif :** re-probe périodique (compteur d'essais) ou épingler
`Unsupported` uniquement sur 403 + `valid-sync-token`.

### 5. La validation iCalendar rejette des corps valides (défaut sur les PUT)

**Où :** `src/caldav/validation.rs:106-110` (pas de dépliage), `:112-119` (BOM)

Le scan structurel (niveau `Structural`, **défaut** des PUT) trimme chaque
ligne mais ne déplie jamais les continuations RFC 5545 §3.1 (lignes
commençant par espace/tabulation). Une `PRODID`/`VERSION`/`UID` pliée
devient invisible → `MissingProdId`/`UnsupportedVersion`/`MissingUid` sur
des calendiers parfaitement valides ; une continuation commençant par
`BEGIN:`/`END:` corrompt la pile de composants → `UnbalancedComponents`.
Un BOM UTF-8 avant `BEGIN:VCALENDAR` échoue aussi (`MissingBegin`).

**Reproduction (sans serveur) :**

```rust
// body valide, PRODID pliée à 75 octets (RFC 5545 §3.1) :
let body = "BEGIN:VCALENDAR\r\nVERSION:2.0\r\nPRODID:-//X//Y\r\n Z//EN\r\nEND:VCALENDAR\r\n";
// validate_icalendar_level(body, ValidationLevel::Structural)
// → Err(InvalidICalendar { violation: MissingProdId })
```

**Correctif :** déplier les continuations (fusionner les lignes commençant
par espace/tab) avant le scan ; ignorer le BOM.

### 6. Credentials envoyés à toute URL absolue fournie par l'appelant

**Où :** `src/webdav/client.rs:684-689` (`build_uri` pass-through), attachement
auth au premier hop ; `strip_credentials` ne joue que sur les sauts de
redirection (`:1177-1185`)

`build_uri` accepte une URL `http(s)://` absolue verbatim, et
`build_and_send` attache l'en-tête `Authorization` (statique ou du token
provider) à ce premier hop sans vérifier l'origin. Un href contrôlé par le
serveur (`client.get(&item.href)`) fait fuiter Basic/Bearer vers un origin
arbitraire. La doc mentionne le pass-through, jamais l'implication auth.

**Reproduction :** client sur `https://dav.example` avec Basic auth ;
`client.get("https://hostile.example/f")` → requête envoyée avec
`Authorization: Basic …` vers `hostile.example` (observable sur un mock).

**Correctif :** comparer host/port à la base avant d'attacher l'auth
(ou ne jamais attacher l'auth sur URL absolue ≠ base).

### 7. `token_endpoint` OAuth2 accepte `http://` — secrets en clair

**Où :** `src/webdav/auth.rs:256-259` (parse sans check https), `:307-343` (POST form)

`OAuth2RefreshProvider::new` parse l'URI mais n'exige pas `https` :
un endpoint `http://` accepte silencieusement et POST `client_secret` +
`refresh_token` en clair, pendant que la doc DAV côté client martèle le
cleartext partout.

**Reproduction :**

```rust
OAuth2RefreshProvider::new("http://token.example/oauth/token", client_id, client_secret, refresh_token).await
// → Ok(provider) ; chaque refresh POSTe les secrets sur http://
```

**Correctif :** rejeter non-https à la construction (ou documenter fort +
warn).

### 8. Matching XML par local-name sans résolution de namespace

**Où :** `src/webdav/streaming.rs:293-379` ; `local_name` à `:1279-1284`

Tous les éléments multistatus sont reconnus par local-name seul : un
`<x:href xmlns:x="urn:vendor">` (namespace étranger) est traité comme un
élément DAV. Les préfixes themselves sont OK (`D:`, `C:`, namespace par
défaut — le préfixe est strippé), mais l'URI de namespace n'est jamais
comparé.

**Reproduction :** `parse_multistatus_bytes` sur un 207 contenant
`<x:href xmlns:x="urn:mal">/pwned</x:href>` → `item.href == "/pwned"`
(interprété comme un href DAV légitime).

**Correctif :** tracker les bindings namespace (quick-xml
`resolve_namespaces`) et comparer l'URI complet pour `href`, `getetag`,
`propstat`, `status`, etc.

### 9. Entité XML inconnue aborte le parse entier

**Où :** `src/webdav/streaming.rs:944-950`

`decode_text` → `unescape` (quick-xml 0.41, entités prédéfinies + numériques
seulement) : toute entité custom/DTD (`&nbsp;`, `&foo;`) produit une erreur
qui remonte en `Error::Xml` et **abort le PROPFIND/REPORT complet**.
Aucun risque XXE/billion-laughs (pas de traitement DTD), mais une entité
inconnue convertit un parse en erreur dure.

**Reproduction :** 207 contenant `<D:displayname>Cal&nbsp;1</D:displayname>`
→ tout l'appel échoue au lieu de retourner le texte brut.

**Correctif :** remplacer/ignorer les entités inconnues (texte littéral)
au lieu de propager l'erreur.

### 10. Mémoire non bornée côté parsing streaming

**Où :** `src/webdav/streaming.rs:670-706` ; `src/common/compression.rs:223-230`

(a) Sur le chemin **streaming**, `calendar_data`/`address_data`/`calendar_timezone`
s'accumulent dans des `String` par item sans aucun cap — le cap 256 MiB de
`decompress_body` ne couvre que le chemin agrégé. Un serveur hostile avec un
seul item de plusieurs Go fait croître la mémoire sans borne.
(b) `decompress_body` lit jusqu'à `MAX_DECOMPRESSED_SIZE + 1` dans un `Vec`
heap **avant** le cap-check : ~256 MiB alloués avant rejet (bombe à la
décompression coûteuse mais bornée).

**Reproduction :** fixture hyper en streaming qui envoie un seul
`<CALDAV:calendar-data>` de >4 GiB → RSS croît sans limite ;
ou corps compressé se décompressant à 300 MiB → allocation de ~256 MiB
avant rejet.

**Correctif :** cap par item dans `handle_text` + cap-check streaming
(abort dès franchissement, sans bufferiser) ; baisser le plafond global.

### 11. Coverage CI sans `--all-features`

**Où :** `.github/workflows/coverage.yml:56-61`

Le step coverage omet `--all-features` alors que la commande documentée
dans AGENTS.md l'inclut : le code sous `#[cfg(feature = "tracing")]` n'est
jamais compté, et `sonar-project.properties` analyse `src/` sans visibilité
sur ces chemins → gate SonarCloud aveugle sur cette partie.

**Reproduction :** comparer `cargo llvm-cov nextest --test unit_tests --profile ci --lcov`
(tel que la CI) avec la commande AGENTS.md (`--all-features`) : le lcov de
la CI ne contient aucune ligne du code feature-gated.

**Correctif :** ajouter `--all-features` à coverage.yml:56-61.

### 12. Parser FREEBUSY : lignes pliées perdues, param quoted tronqué

**Où :** `src/caldav/client.rs:1052-1088`

Le parser FREEBUSY est naïf : pas de dépliage RFC 5545 (les continuations
sont ignorées → **périodes perdues silencieusement**), et `split_once(':')`
tronque les params si un param quoted contient `:`.

**Reproduction (filaire) :** réponse `free-busy-query` avec :

```
FREEBUSY;FBTYPE=BUSY:20260908T090000Z/20260908T1
 00000Z
```

(ligne pliée) → période non retournée, sans erreur.

**Correctif :** déplier les lignes avant le parse ; parser les params
quoted-aware.

### 13. Paramètres XML publics interpolés sans échappement

**Où :** `src/webdav/xml.rs:133, 251-252` (`namespace`, `root_element`,
`data_element`)

`build_sync_collection_body`/`build_multiget_body` sont `pub` et interpolent
ces chaînes telles quelles dans le XML généré. Tous les call-sites internes
passent des constantes `&'static str` (aucune injection vivante), mais
l'API publique permet l'injection XML par un appelant externe. Les valeurs
de données (tokens, hrefs, text-match…) sont, elles, correctement échappées.

**Reproduction :**

```rust
build_sync_collection_body(iter::empty(), false, None, "DAV:\"><D:hack/>", "x", "y", SyncLevel::One)
// → xmlns:C="DAV:"><D:hack/>" injecté dans le corps
```

**Correctif :** `escape_xml` sur ces trois params (ou les rendre
non-pub/type-safe).

### 14. Timeouts zéro acceptés par le builder

**Où :** `src/webdav/builder.rs:265-268` (`connect_timeout`), `:293-296` (`pool_idle_timeout`)

`build()` valide `timeout > 0` et `pool_max_idle_per_host > 0` mais accepte
`connect_timeout(Duration::ZERO)` (connect échoue instantanément) et
`pool_idle_timeout(ZERO)` (keep-alive désactivé silencieusement).

**Reproduction :**

```rust
WebDavClientBuilder::new().base_url("https://…")?.connect_timeout(Duration::ZERO).build()
// → Ok(client) ; toutes les connexions échouent immédiatement
```

**Correctif :** valider `> 0` comme pour les autres champs.

## 🔵 LOW

### 15. `Lock-Token` / `Destination` survivent à une redirection cross-origin

**Où :** `src/webdav/client.rs:1177-1185` — seuls `Authorization`, `Cookie`,
`If-Match`, `If-None-Match` sont strippés. Repro : `UNLOCK` (ou `MOVE` avec
`Destination`) vers un serveur qui 302 cross-origin → l'en-tête `Lock-Token`
(capability URL) et l'URL interne `Destination` partent vers l'hôte de
redirection. **Fix :** étendre la liste de strip.

### 16. Avertissement `danger_accept_invalid_certs` absent en release

**Où :** `src/webdav/builder.rs:784-788` — le warning est
`#[cfg(debug_assertions)]` : en release, activer NoVerify est silencieux.
Le flag reste opt-in/défaut-off/documenté. Repro : `cargo build --release`
avec `danger_accept_invalid_certs(true)` → aucun avertissement.
**Fix :** `tracing::warn!` inconditionnel (la feature existe déjà).

### 17. `multiget_data` ignore le statut par-item

**Où :** `src/webdav/sync.rs:559-565` — un membre écho avec 404 (supprimé
entre sync-collection et multiget) ne contribue ni donnée ni erreur :
`entry.data == None`, indistinguable d'une propriété absente. Repro :
fallback sync avec data ; multiget 207 où un membre porte
`<D:status>HTTP/1.1 404 Not Found</D:status>` → item présent dans
`added/modified` avec `data: None`, rien dans `deleted`. **Fix :** check
`item.status` → skip explicite ou erreur.

### 18. Matching href par égalité stricte

**Où :** `src/webdav/multiget.rs:96-102` — `missing_hrefs` compare les hrefs
en égalité exacte : un serveur qui ré-écho des hrefs équivalents-mais-différents
(absolu vs relatif, `%XX` différent) marque **tout** `missing` (items quand
même livrés — documenté). Repro : multiget avec hrefs relatifs, réponse 207
en hrefs absolus → `missing` non vide. **Fix :** normalisation de href avant
comparaison.

### 19. Balises comparées case-insensitive

**Où :** `src/webdav/streaming.rs:296-375` — `<HREF>`/`<RESPONSE>` (distincts
en XML) sont acceptés comme `href`/`response`. Laxiste envers les serveurs
cassés, anti-spec. Repro : 207 avec `<D:HREF>x</D:HREF>` → parsé comme href.
**Fix :** décision produit : serrer (casser les serveurs non conformes) ou
documenter la tolérance.

### 20. `retry_all=true` re-tente des writes non idempotents (opt-in)

**Où :** `src/webdav/client.rs:1112-1113`, `src/webdav/retry.rs:28-35` — avec
l'option (défaut off), PUT/DELETE sont re-tentés sur 503/504 ; si l'origin a
appliqué le write avant le timeout gateway, le retry double la création /
écrase contre un etag déplacé. La politique par défaut est saine (jamais de
retry non-idempotent). Repro : `retry_all(true)`, PUT derrière un gateway
504 après write appliqué → deuxième PUT émis. **Fix :** documenter le risque
duplication à côté du flag (déjà partiellement fait).

### 21. Pas de single-flight sur la capacité sync

**Où :** `src/webdav/sync.rs:309-320` — `capability()` et le read-modify-write
de token/`prev` se font hors verrou : deux clones appelant `incremental()`
en parallèle font deux probes, deux REPORTs identiques, dernier écrivain
gagnant (deltas possiblement doublés). Repro : deux `tokio::spawn` sur des
clones de session au premier `incremental()`. **Fix :** single-flight
(tokio Mutex déjà utilisé ailleurs) autour de la probe et du RMW d'état.

### 22. `Location: "#frag"` résolu avec query perdue

**Où :** `src/webdav/client.rs:333-346` — un `Location` fragment-only
résout vers le path courant avec la query courante perdue (RFC 3986 §5.3).
Pathologique mais faux. **Fix :** conserver la query sur résolution
fragment-only.

### 23. Parsing HTTP-date tolérant/faux

**Où :** `src/webdav/retry.rs:126-142` — `parse_http_date` accepte des dates
impossibles (31 février → délai calculé faux) et rejette la seconde
intercalaire `:60` (fallback backoff, bénin). Repro :
`Retry-After: Tue, 31 Feb 2026 00:00:00 GMT` → délai erroné. **Fix :**
accepter seulement les dates valides.

### 24. Token brut écho dans le message d'erreur

**Où :** `src/webdav/client.rs:1613-1615` — `validate_lock_token` interpole
le token appelant dans `Error::InvalidInput` (`{token:?}`). Pas un secret,
mais incohérent avec la discipline de redaction du reste. **Fix :**
tronquer/élider la valeur dans le message.

### 25. Doc scheduling contredit le code ; Content-Type asymétrique

**Où :** `src/caldav/scheduling.rs:124-140` — la doc dit qu'un tag contenant
une quote « produit une valeur d'en-tête malformée », mais le code le
rejette pre-I/O avec `Error::InvalidInput` (la section `# Errors` dit le
contraire de la doc). Et `:473-476` — `put_if_schedule_tag` envoie
`text/calendar` sans le param `version` que `put`/`prepare_ical_put`
dérivent. **Fix :** corriger la doc ; aligner le Content-Type.

### 26. CardDAV : aucune validation vCard, non documenté

**Où :** `src/carddav/client.rs:568-609` — CalDAV a `ValidationLevel`
(défaut Structural), CardDAV envoie les vCards sans aucune validation
(sniff `VERSION` pour le Content-Type seulement). Le README scope la
validation iCal à CalDAV mais ne dit nulle part que CardDAV n'en fait pas.
**Fix :** le dire explicitement (README + doc de `put_contact`) ou ajouter
une validation symétrique.

## Faux positif écarté (à ne pas « corriger »)

**coverage.yml `--profile ci` est valide.** `cargo build --profile ci`
échoue bien (`profile 'ci' is not defined` — aucun `[profile.ci]` dans
Cargo.toml), mais `cargo llvm-cov nextest --test unit_tests --profile ci`
passe : avec le sous-command `nextest`, cargo-llvm-cov transmet `--profile`
à **nextest** (profil défini dans `.config/nextest.toml`), pas à cargo.
Vérifié localement le 2026-09-08 ; la workflow Coverage & Analysis passe
sur GitHub. Le vrai problème de ce step est l'absence de `--all-features`
(finding 11).

## Ce qui a été vérifié et est sain (pour ne pas re-auditer)

- **Pas d'`unsafe`, pas de panic en lib** : les 4 `unwrap/expect` hors tests
  sont gardés par invariants (sémaphore privé jamais closed, `Depth` enum,
  requêtes statiques) — commentés `ponytail:` sur place.
- **Zeroize réellement utilisé** : `Drop` sur les champs du builder,
  intermédiaires avant le `?` de retour fallible, proxy Basic, token du
  provider, tokens OAuth en cache. Limite assumée : la copie vive dans le
  `HeaderValue` n'est pas zeroizée (documenté).
- **Redirections** : cross-origin strippe `Authorization`/`Cookie`/`If-Match`/`If-None-Match`,
  https→http jamais suivi, 303 drop le body, pas de double-hop (hyper suit
  0 redirection lui-même).
- **ETag conditionnel** : tags weak rejetés sur `If-Match` (RFC 9110),
  etag vide échoue pre-I/O, `If-None-Match: *` pour create-only.
- **Retry par défaut sûr** : GET/HEAD/OPTIONS/PROPFIND/REPORT seulement,
  jamais sur timeout/transport (le timeout propage), bornes strictes,
  `Retry-After` clampé (serveur hostile ne peut pas planter l'appelant).
- **URL/encoding** : `?`/`#` encodés par segment, `%XX` valides préservés,
  pas de double slash ; hrefs/tokens échappés dans les corps XML.
- **Multiget** : chunking sans off-by-one, `batch_size == 0` rejeté,
  semaphore sans fuite, isolation par chunk, ordre préservé.
- **XML** : pas d'XXE (pas de résolution d'entités externes), pas de
  récursion (parsing itératif), XML tronqué jamais retourné en partiel
  silencieux (`finish()` rejette les éléments non fermés), backpressure
  réelle (await par event, buffer réutilisé, timeout par lecture).
- **Auth OAuth** : un seul refresh+retry par requête, single-flight du
  refresh, réponse token plafonnée à 1 MiB, erreurs OAuth sans corps de
  réponse.
- **Pas de duplication CalDAV/CardDAV** : `streaming.rs` des deux côtés =
  9 lignes de ré-exports ; le gros du machinerie est délégué via
  `impl_dav_client_delegates!` (webdav/client.rs:2367-2869) et
  `impl_dav_builder!` (webdav/builder.rs:910-1090). Duplication résiduelle =
  adaptateurs fins (24-25 lignes identiques par paire, Info).
- **Docs vs code** : 10+ symboles spot-checkés dans le README existent tous
  (post_managed_attachment, set_calendar_timezone, current_user_privileges,
  discover_caldav/carddav, free_busy_query, LockInfo/LockScope, Retry-After,
  DavItem.managed_ids…) ; 65 noms de méthodes du CHANGELOG résolvent tous ;
  pas de claim fantôme ; les gates AGENTS.md tournent bien en CI (fmt,
  clippy -D warnings, nextest, doc tests, MSRV, audit, semver-checks).
